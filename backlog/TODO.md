# TODO

所有待辦與想法的索引。開始做某項時依 CLAUDE.md 的功能開發流程進行。

分成四組：

- P0～P2：確定要處理的事，依重要程度分組，做法還沒決定的也放這裡
  - P0：影響核心價值，或擋住主線（web app 第 2 階段）
  - P1：單獨做就有價值
  - P2：改善，不做也不影響使用
- 待評估：還沒決定要不要做的想法，放在最後

同一組內的順序：

- 大致依建議的順序排列
- 要等條件成立的項目排在該組最後

每項一個標題：

- 標題用動詞開頭寫出要做什麼（例如加入、修正、決定），不放標點
- 別的文件可以直接連到該項

P0～P2 的項目在標題下依序寫：

- 為什麼：不做會怎樣
- 影響的功能：做這項時要改程式或文件的功能，寫法：
  - 寫[功能清單](../docs/product/overview.md#功能清單)的功能 ID，多個時一個功能一項子項
  - 還沒有功能 ID 的新功能寫「新功能」
  - 改的是所有功能共用的慣例時寫「全部」
  - 和產品功能無關的（例如 AI coding 工作流、notebook）寫「無」
- 條件：要等條件成立才能開始的才寫，成立後刪掉這一行
- 進行中：已開工、一次做不完的才寫
  - 格式是「進行中：<開始日期>，進度見 <連結>」
  - 做完連同項目刪除
  - 功能的進度以 [overview 的功能清單](../docs/product/overview.md#功能清單)為準，這裡只連過去
- 依賴：有前置任務的才寫
- 其餘細節：做法、開工時要決定的事
  - 超過約三行時移到細節檔，這裡改寫「細節見 [tasks/<名稱>.md](…)：細節有哪些」

確定要做決定、但還沒決定怎麼做的取捨，標題用「決定」開頭：

- 只有大到要寫成決策紀錄的取捨才單獨成一項
- 開工時順手決定的小事，寫在實作項目的「開工時要決定的事」
- 細節寫候選做法與怎麼決定
- 做完的定義是把結果寫成決策紀錄並更新相關文件
- 決定後還有實作要做時，改寫成實作項目，或併進依賴它的項目

「待評估」的項目在標題下寫：

- 想解決什麼
- 影響的功能：寫法同 P0～P2
- 怎麼決定：要看什麼資料，或等什麼情況出現才判斷
  - 寫不出來的通常只是一閃而過的念頭，先不要收進來
- 細節超過約三行時移到 `ideas/` 的細節檔，寫法同 `tasks/`

細節檔放在 `tasks/`、`ideas/`，需要時才開：

- 檔名用英文 kebab-case
- 開頭連回這裡的項目
- 不重複條件、為什麼等欄位，改的時候只改一處
- 其他文件連到某項時，有細節檔的連到細節檔，沒有的連到這裡的標題

項目離開這份索引的方式：

- 做完：刪除項目與細節檔，同時更新其他文件中連到該項的連結
- 待評估的想法決定做：
  - 補齊 P0～P2 的欄位，移到對應的組
  - 細節檔從 `ideas/` 移到 `tasks/`
  - 同時更新其他文件中連到它的連結
- 決定不做：刪除項目與細節檔，不做的理由值得留下時寫成決策紀錄

## P1：單獨做就有價值

### 補上需要網路的測試的慣例

- 為什麼：沒寫清楚的話，需網路的測試因外部服務出錯而失敗時，容易被當成不通過，或為此放寬驗收
- 影響的功能：全部
- 做法：在 [development.md](../docs/conventions/development.md#測試) 的測試慣例補上：
  - 業務規則由離線測試驗證，外部服務以固定回應代替
  - 需網路的測試只驗真實串接：API 接得通、回應合格
  - 需網路的測試因外部服務錯誤（逾時、限流、服務中斷）失敗時重跑，不算不通過，也不為此放寬驗收

### 標出過時的評分

- 為什麼：分數過時了也沒有提示
  - 職缺重新爬取後內容變了，或改了淘汰條件等設定，已經有評分的職缺不會被整批重評，舊分數一直留著
  - 目前只能以 `--job-no` 指定重評
  - 第 2 階段能在職缺表勾選重評，但仍看不出哪些分數過時
- 影響的功能：
  - job-database
  - job-auto-scoring
- 細節見 [tasks/stale-scores.md](tasks/stale-scores.md)：內容變更的判斷、記錄與標示的做法、開工時要決定的比對基準與門檻

### 拆開地區欄位

- 為什麼：
  - 104 本來就分開提供縣市行政區與街道地址，爬蟲卻用空白合成 `地區` 一欄，名稱也和內容不符
  - 職缺表的地區篩選因此也會比對到街道名稱
- 影響的功能：
  - 104-job-scraper
  - job-database
- 做法：
  - 把 `地區` 拆成 `縣市行政區` 與 `街道地址`
  - web app 的地區篩選改成只比對縣市行政區
  - 既有資料用「先備份再遷移」處理

### 做趨勢圖表

- 為什麼：
  - 看出職缺的趨勢（UP-04）
  - 看出自己的興趣分佈（UP-05），要等標記累積資料才看得出來
- 影響的功能：trend-analysis
- 條件：職缺表完成
- 細節見 [tasks/trend-charts.md](tasks/trend-charts.md)：交付形式、規劃時要決定的執行紀錄去留

## P2：改善，不做也不影響使用

### 加入通勤便利度維度

- 為什麼：評分目前不考慮通勤，同樣條件的職缺分不出遠近
- 影響的功能：job-auto-scoring
- 候選做法：
  - 依行政區分級，加上捷運標籤加分
  - 用地圖 API 計算實際通勤時間

### 加入資歷門檻與工作型態維度

- 為什麼：評分看不到年資要求與遠端、彈性工時等工作型態，因為爬蟲沒有輸出這些欄位
- 影響的功能：
  - 104-job-scraper
  - job-database
  - job-auto-scoring
- 做法：
  1. 擴充爬蟲欄位（年資要求、遠端等工作型態），並加進職缺欄位契約
  2. 在評分加上兩個維度：
     - 資歷門檻
     - 工作型態與福利（遠端、彈性工時等）

### 顯示競爭程度與新鮮度

- 為什麼：應徵人數、更新日期能幫忙判斷值不值得投
- 影響的功能：job-auto-scoring
- 做法：當參考資訊或篩選條件，不適合算進總分

### 評分失敗時立即重試

- 為什麼：
  - 目前單筆 AI 呼叫失敗會跳過該筆繼續，沒有寫進資料庫
  - 要等下次執行才會再評
- 影響的功能：job-auto-scoring
- 做法：同一次執行內，單筆 AI 呼叫失敗時立即重打

### 修正薪資欄位的排序

- 為什麼：職缺表照存的值排序，依薪資排序時順序不對：
  - 面議時 `薪資下限`、`薪資上限` 是 `0`，面議的職缺排在最低
  - 沒有上限時 `薪資上限` 是 `9999999`，「以上」的職缺排在最高
- 影響的功能：job-database
- 開工時從兩種做法擇一：
  - 這些值排序時當成沒有值，排在最後
  - 改用換算後的月薪排序

### 去掉職缺代碼的前後空白

- 為什麼：
  - 前後有空白的代碼存進 `jobs` 後，和評分紀錄 JOIN 不到
  - 拿掉手動評分後，評分都來自資料庫裡的職缺，實際碰到的機會很小
- 影響的功能：job-database
- 做法：寫入職缺時去掉 `職缺代碼` 的前後空白，不在評分端處理

### 修正 commit-review README 中一句多概念的寫法

- 為什麼：
  - [README 的設計重點與理由](../.claude/skills/commit-review/README.md#設計重點與理由)有些項目一句話包含好幾個概念，例如「擋 commit」那項，違反 [documentation.md 的格式](../docs/conventions/documentation.md#格式)
  - 寫新內容時會照著這個密度寫
- 影響的功能：無
- 做法：逐句檢查整份 README，一句多概念的改成條列

### 把職缺欄位契約改成平台中立

- 為什麼：
  - 目前的欄位取自 104 職缺
  - 執行紀錄的條件欄位（`關鍵字`、`地區`、`職缺性質`、`頁數`、`來源檔`）也是 104 留下的形狀
- 影響的功能：
  - job-database
  - 104-job-scraper
- 條件：接第二個求職平台
- 要處理：
  - 跨平台的職缺識別（現在的 `職缺代碼` 就是 104 的 `jobNo`）
  - 來源平台欄位
  - 各平台特有欄位怎麼放
- 同時規劃在網頁上手動新增一筆職缺（例如貼上其他平台的職缺），非 104 的職缺要先決定：
  - 代碼怎麼產生
  - 要不要加來源平台欄位
  - 哪些欄位必填

## 待評估：還沒決定要不要做

### 把文件格式規則移到更顯眼的位置

- 想解決什麼：寫文件時，「格式」一節最容易被忽略
  - [documentation.md](../docs/conventions/documentation.md) 有一半在講功能文件、FR／AC 與技術設計
  - 寫 skill README 這類文件時，用得到的只有「內容」與「格式」兩節，而「格式」排在最後
- 影響的功能：無
- 怎麼決定：commit 前改由 subagent 檢查格式（見 [commit-review 的設計重點](../.claude/skills/commit-review/README.md#設計重點與理由)）後，仍常被指出違反格式規則時再做
- 候選做法：
  - 把「格式」獨立成短檔
  - 移到 documentation.md 最前面
