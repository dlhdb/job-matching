## 1. 背景與目標

104 爬蟲（F2-01）一次可能抓回上百筆職缺，但 F1-01 的評分一次只能處理一筆，使用者得自己一筆一筆執行 CLI、再手動比較分數高低。這個功能把整個職缺 JSON 陣列一次評完，依總分排序、清楚標示被淘汰與評分失敗的職缺，讓使用者一次就能看出這批職缺裡最值得細看的是哪幾筆（UC-02）。

v1 只處理職缺評分；「給公司打分」（UC-03）留待 F3（擷取公司資訊與評價）完成後再擴充。

## 2. 使用情境

- 身為求職者，我想要把一整批爬到的職缺一次送進評分，而不用一筆一筆手動執行 CLI，以便快速看出這批職缺裡哪些最值得細看。
- 身為求職者，我想要評分結果依總分排序、並清楚標示被淘汰或評分失敗的職缺，以便直接從結果檔案挑出前幾名去細看，不用自己整理。
- 身為求職者，我想要評分中途若有個別職缺失敗，其餘職缺仍能跑完，以便不會因為一兩筆問題浪費整批已經花費的時間與 AI 費用。

## 3. 範圍

**範圍內**

- 讀取 F2-01 輸出的職缺 JSON 陣列（整批，而非單筆）。
- 對每一筆職缺重複使用 F1-01 既有的評分邏輯（硬性淘汰 → 薪資規則 → AI 三維度評分 → 加權總分），沿用其輸出欄位定義。
- 硬性淘汰的職缺不呼叫 AI（沿用 F1-01 既有保證）。
- 個別職缺評分失敗（AI 呼叫錯誤或回應驗證失敗）時記錄失敗原因並跳過，繼續處理下一筆，不中斷整批。
- 產出 JSON（完整結構）與 CSV（攤平表格）兩種結果檔案，皆依總分由高到低排序；無總分（被淘汰或失敗）的職缺排在有總分職缺之後，並清楚標示原因。
- 執行結束後回報摘要（總筆數、成功、淘汰、失敗筆數與輸出位置）。

**範圍外**（實作時不要做）

- 公司評分——等 F3 完成後再擴充「產業公司吸引力」維度或另開功能。
- 評分結果的重試機制——單筆失敗一律跳過，不自動重打 AI（見 [TODO.md](../../TODO.md)）。
- 評分結果快取——重跑同一批一律重新呼叫 AI，不比對是否已評過（見 [TODO.md](../../TODO.md)）。
- 並行/平行處理多筆 AI 呼叫——本次維持循序執行。
- 修改 F1-01 既有的單筆評分邏輯、維度定義、淘汰規則或加權方式。
- 互動式瀏覽/篩選介面——只產出檔案。

## 4. 功能需求

每條需求要能被至少一條驗收標準涵蓋。

- **FR-1**：讀取指定的職缺 JSON 檔案（F2-01 輸出格式），取得該批全部職缺。
- **FR-2**：對每一筆職缺依序執行 F1-01 的評分流程；被硬性淘汰的職缺不呼叫 AI。
- **FR-3**：職缺評分過程中若發生錯誤（AI 呼叫失敗或回應驗證失敗），記錄該筆失敗原因並跳過，繼續處理下一筆，錯誤不得中斷整批。
- **FR-4**：整批結果（成功評分／被淘汰／評分失敗三類）依總分由高到低排序；無總分的職缺排在有總分職缺之後。
- **FR-5**：輸出 JSON 與 CSV 兩種格式的結果檔案；CSV 需可用 Excel 正常開啟中文（比照 F2-01 使用 utf-8-sig）。
- **FR-6**：執行結束回報摘要：總筆數、成功評分筆數、被淘汰筆數、失敗筆數、輸出檔案位置。

## 5. 設計

實作規劃時補上。目前已確定的資料契約：

- **輸入**：F2-01 輸出的職缺 JSON 陣列（欄位見 [F2-01 §5.5](F2-01-104-job-scraper.md#55-欄位字典)）；與 F1-01 相同的 `preferences.yaml`、`experience.md`（格式見 [F1-01 §5.2](F1-01-job-scoring.md#52-輸入個人資料檔)）。
- **輸出**：一份 JSON 檔與一份 CSV 檔，內容為每筆職缺的評分結果——成功評分沿用 F1-01 的 `JobScore` 欄位（[F1-01 §5.7](F1-01-job-scoring.md#57-輸出jobscore)）；被淘汰的職缺標示淘汰與淘汰原因；評分失敗的職缺標示失敗原因；皆依總分排序。存放位置與檔名慣例在實作規劃時決定。
- **缺值處理**：沿用 F1-01 與 F2-01 既有規則——職缺欄位缺值一律 `null`、不回填；AI 判斷資料不足時該維度給 `null`；評分失敗的職缺沒有總分與維度分數，只有失敗原因。

## 6. 驗收標準

尚未進入實作規劃，驗收標準先以行為描述；對應的檔名與函式名稱在實作規劃時補上。

### AC-1：整批評分成功且排序正確（涵蓋 FR-1、FR-2、FR-4）

- **Given**：一份含多筆職缺（含會被淘汰與正常職缺）的 JSON 檔，以及有效偏好檔
- **When**：執行批次評分
- **Then**：輸出結果包含每筆職缺的評分或淘汰標示，且依總分由高到低排序，無總分職缺排在後面
- **驗證方式**：批次評分模組測試（實作規劃時補上檔名與函式名）
- **通過條件**：全部 passed，且人工檢查排序正確

### AC-2：個別職缺失敗不中斷整批（涵蓋 FR-3）

- **Given**：一份多筆職缺 JSON 檔，其中一筆會讓假 LLM client 丟出錯誤
- **When**：執行批次評分
- **Then**：該筆標示失敗並附原因，其餘職缺正常完成評分
- **驗證方式**：（實作規劃時補上）
- **通過條件**：全部 passed

### AC-3：被淘汰職缺不呼叫 AI（涵蓋 FR-2）

- **Given**：一份含會被硬性淘汰之職缺的 JSON 檔
- **When**：執行批次評分
- **Then**：該筆標示淘汰，測試用假 client 從未被呼叫
- **驗證方式**：（實作規劃時補上）
- **通過條件**：全部 passed

### AC-4：輸出檔案格式正確（涵蓋 FR-5）

- **Given**：一批評分結果
- **When**：寫出 JSON 與 CSV 檔案
- **Then**：JSON 可解析且欄位完整；CSV 以 utf-8-sig 可正確讀出中文欄位
- **驗證方式**：（實作規劃時補上）
- **通過條件**：全部 passed

### AC-5：執行摘要正確（涵蓋 FR-6）

- **Given**：一批含成功、淘汰、失敗三種結果的評分
- **When**：執行結束
- **Then**：終端機印出的摘要數字（總筆數/成功/淘汰/失敗）與實際結果相符
- **驗證方式**：（實作規劃時補上）
- **通過條件**：全部 passed

### AC-6：真實批次評分 〔需網路〕（涵蓋 FR-1～FR-6）

- **Given**：F2-01 最新一次爬取的真實職缺 JSON 檔與真實偏好檔
- **When**：對整批職缺執行批次評分
- **Then**：輸出檔案排序合理，被淘汰與失敗筆數均有清楚原因
- **驗證方式**：`uv run pytest -m network ...`（實作規劃時補上）
- **通過條件**：passed，且使用者人工抽查前幾名職缺的評分理由是否合理
