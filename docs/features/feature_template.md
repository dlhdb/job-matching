### 4.1 需求

每條需求要能被本章至少一條驗收標準驗到。新故事對既有需求的改動，寫成新故事自己的需求，不改既有故事的需求。ID 格式是 `FR-<故事 slug>-<重點>`，命名規則見 [documentation.md](../conventions/documentation.md#功能文件的結構)。一條需求有多個重點時，首行只寫核心要求，條件、例外與附帶規則用子項列開，不要用「；」串成長句。

- FR-<slug>-<重點>：核心要求。
  - 條件或例外。
  - 附帶規則。
- FR-<slug>-<重點>：只有一個重點時就寫成一行。

### 4.2 設計

只寫程式碼講不出來的事：流程、規則與其理由、外部系統的限制、資料契約、缺值處理（依 [development.md](../conventions/development.md#防禦性設計)，缺值為 `null`，不回填）。考慮過其他做法的取捨，連到 [決策紀錄](../decisions/)，不在這裡重寫理由。內容分項時往下開一層小節，需求與驗收用 `#421-小節名稱` 這樣的錨點直接連過來。

### 4.3 驗收

每條都要寫出可實際執行的驗證方式與明確的通過條件，不寫「運作正常」這類無法判定的描述。ID 格式是 `AC-<故事 slug>-<重點>`，命名規則見 [documentation.md](../conventions/documentation.md#功能文件的結構)。

- 驗證方式優先寫成 pytest 指令，例如 `uv run pytest tests/test_x.py -k <函式名>`。測試程式與實作一起撰寫，不要把腳本貼在功能文件裡（測試慣例見 [development.md](../conventions/development.md#測試)）。
- 「輸入 → 預期結果」可以逐項條列留在功能文件（`- 輸入 → 預期結果`），測試再用 `parametrize` 實作。
- 需要網路或外部服務的條目，標題標註 `〔需網路〕`，測試放在 `tests/e2e/` 並加上 `@pytest.mark.network`，驗證方式寫 `uv run pytest -m network tests/e2e/...`。
- 只能由人判斷的部分（例如 AI 的理由是否合理），在通過條件中明確寫出由誰判斷、看什麼。

#### AC-<slug>-<重點>：<標題>

- Given：前置條件
- When：執行的動作
- Then：預期結果
- 驗證方式：`uv run pytest tests/test_<模組>.py -k <函式名>`
- 通過條件：全部 passed。
