每條需求要能被至少一條驗收標準涵蓋。ID 格式是 `FR-<系統能力 slug>-<重點>`，命名規則見 [conventions.md](../conventions.md#功能文件的結構)。一條需求有多個重點時，首行只寫核心要求，條件、例外與附帶規則用子項列開，不要用「；」串成長句。

### 5.3 驗收

每條都要寫出**可實際執行**的驗證方式與明確的通過條件，不寫「運作正常」這類無法判定的描述。ID 格式是 `AC-<系統能力 slug>-<重點>`，命名規則見 [conventions.md](../conventions.md#功能文件的結構)。

- 驗證方式優先寫成 pytest 指令，例如 `uv run pytest tests/test_x.py -k <函式名>`。測試程式與實作一起撰寫，不要把腳本貼在功能文件裡（測試慣例見 [conventions.md](../conventions.md#測試)）。
- 「輸入 → 預期結果」可以寫成表格留在功能文件，測試再用 `parametrize` 實作。
- 需要網路或外部服務的條目，標題標註 `〔需網路〕`，測試放在 `tests/e2e/` 並加上 `@pytest.mark.network`，驗證方式寫 `uv run pytest -m network tests/e2e/...`。
- 只能由人判斷的部分（例如 AI 的理由是否合理），在通過條件中明確寫出由誰判斷、看什麼。

#### AC-<slug>-<重點>：<標題>（涵蓋 FR-<slug>-<重點>）

- **Given**：前置條件
- **When**：執行的動作

- **驗證方式**：`uv run pytest tests/test_<模組>.py -k <函式名>`
- **通過條件**：全部 passed。
