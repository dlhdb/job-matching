## 3. 輸入與輸出

- 輸入：讀哪些資料、來自哪個功能。
- 輸出：產出什麼、給哪個功能用。
- 兩者都寫明格式、存放位置與欄位定義。
- 其他功能已經定義的契約，連過去就好，不要複製內容。
- 下游功能需要什麼寫在這裡：
  - 不寫成使用者故事，也不點名是哪個功能。
  - 跨功能的關係只寫在 [overview 的功能依賴](../overview.md#功能依賴)與 architecture.md。

## 4. 故事 A（slug）

<!-- 每個使用者故事一章，是一個可以單獨交付的價值切片：

     - 只是附帶條件的小故事（例如「單筆失敗不中斷整批」）寫成所屬故事的 FR，不單獨成章。
     章名寫使用者能做到的事。故事寫使用者在意的事與好處，不寫實作方式（存在哪裡、用什麼技術）。
     角色只寫求職者或開發者。
     〔規劃中〕標在這裡的第一行，不寫進標題。 -->

身為 <角色>，我想要 <做某件事>，以便 <得到某個好處>。

### 4.1 需求

- 每條需求要能被本章至少一條驗收標準驗到。
- ID 格式是 `FR-<故事 slug>-<重點>`：
  - 故事只有一條需求時，可以省略 `-<重點>`。
- 一條需求有多個重點時，首行只寫核心要求，條件、例外與附帶規則用子項列開，不要用「；」串成長句。

範例：

- FR-<slug>-<重點>：核心要求。
  - 條件或例外。
  - 附帶規則。
- FR-<slug>-<重點>：只有一個重點時就寫成一行。

### 4.2 規則

只寫 PM、設計師需要知道的事，實作方式寫在技術設計：

- 業務規則與其理由，例如計分、淘汰、去重的條件
- 流程：描述動作與資料流，不寫模組、函式或變數名稱
- 使用者接觸到的介面與資料：CLI 參數、設定檔欄位、輸出檔欄位
- 外部系統對使用者有影響的限制，例如請求頻率
- 資料存放：只寫「職缺資料庫」與保存了哪些資訊，不寫資料庫種類、表名、查詢方式與檔案路徑

其他規則：

- 考慮過其他做法的取捨，連到 [產品決策紀錄](../decisions/)，不在這裡重寫理由。
  - 技術取捨寫在 `tech/decisions/`，功能文件不連過去。
- 內容分項時往下開一層小節，需求與驗收用 `#421-小節名稱` 這樣的錨點直接連過來。

#### 4.2.1 <小節>

…

### 4.3 驗收

- 每條都要寫出明確的通過條件，不寫「運作正常」這類無法判定的描述。
- ID 格式是 `AC-<故事 slug>-<重點>`：
  - AC 驗的就是同名 FR 時沿用同一個重點名稱。故事只有一條需求時，可以省略 `-<重點>`。
  - AC 標題只寫 ID 與描述，不列出涵蓋哪些 FR，錨點才不會隨涵蓋清單改變。
- 驗收預設驗同一章的需求：
  - 新故事對既有需求的改動，寫成新故事自己的 FR，既有故事的需求不動，改動的需求和驗收才會在同一章。
  - 驗收順帶驗到別章的需求時不另外標註。每條需求都要有驗收，逐章核對。
- 用業務語言寫情境與看得到的行為，不寫測試手法（理由見[決策紀錄：驗收不寫測試手法](../../conventions/decisions/acceptance-without-test-method.md)）：
  - 寫「一筆會被淘汰的職缺」「AI 呼叫失敗」，不寫 fixture、假物件、`tmp_path` 或函式名稱。
  - 外部服務的回應與失敗寫成情境，例如「AI 回傳 6 分」「104 回應錯誤」。不寫外部服務是真的還是以固定回應代替，也不寫需不需要網路。
  - 驗證方式與指令寫在技術設計的驗收對照。
- 「輸入 → 預期結果」可以逐項條列（`- 輸入 → 預期結果`）。
- Given、When、Then 有多個條件或結果時，用子項列出。
- 只能由人判斷的部分（例如 AI 的理由是否合理），在通過條件中明確寫出由誰判斷、看什麼。

#### AC-<slug>-<重點>：<標題>

- Given：前置條件
- When：執行的動作
- Then：預期結果
- 通過條件：…
