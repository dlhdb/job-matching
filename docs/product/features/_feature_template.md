## 3. 輸入與輸出

- 輸入：讀哪些資料、來自哪個功能。
- 輸出：產出什麼、給哪個功能用。
- 兩者都寫明格式、存放位置與欄位定義。
- 其他功能已經定義的契約，連過去就好，不要複製內容。
- 下游功能需要什麼寫在這裡，不寫成使用者故事。

身為 <角色>，我想要 <做某件事>，以便 <得到某個好處>。

### 4.1 需求

- 每條需求要能被本章至少一條驗收標準驗到。
- 新故事對既有需求的改動，寫成新故事自己的需求，不改既有故事的需求。
- ID 格式是 `FR-<故事 slug>-<重點>`，命名規則見 [documentation.md](../../conventions/documentation.md#功能文件的結構)。
- 一條需求有多個重點時，首行只寫核心要求，條件、例外與附帶規則用子項列開，不要用「；」串成長句。

範例：

- FR-<slug>-<重點>：核心要求。
  - 條件或例外。
  - 附帶規則。
- FR-<slug>-<重點>：只有一個重點時就寫成一行。

### 4.2 規則

只寫 PM、設計師需要知道的事，實作方式寫在技術設計：

- 業務規則與其理由，例如計分、淘汰、去重的條件
- 流程：描述動作與資料流，不寫模組、函式或變數名稱
- 使用者接觸到的介面與資料：CLI 參數、設定檔欄位、輸出檔欄位
- 外部系統對使用者有影響的限制，例如請求頻率
- 資料存放：只寫「職缺資料庫」與保存了哪些資訊，不寫資料庫種類、表名、查詢方式與檔案路徑
- 缺值處理：依 [development.md](../../conventions/development.md#防禦性設計)，缺值為 `null`，不回填

其他規則：

- 考慮過其他做法的取捨，連到 [產品決策紀錄](../decisions/)，不在這裡重寫理由。
  - 技術取捨寫在 `tech/decisions/`，功能文件不連過去。
- 內容分項時往下開一層小節，需求與驗收用 `#421-小節名稱` 這樣的錨點直接連過來。

…

### 4.3 驗收

- 每條都要寫出明確的通過條件，不寫「運作正常」這類無法判定的描述。
- ID 格式是 `AC-<故事 slug>-<重點>`，命名規則見 [documentation.md](../../conventions/documentation.md#功能文件的結構)。
- 用業務語言寫，不寫測試手法：
  - 寫「一筆會被淘汰的職缺」「不實際呼叫 AI」，不寫 fixture、假物件、`tmp_path` 或函式名稱。
  - 驗證指令寫在技術設計的驗收對照。
- 「輸入 → 預期結果」可以逐項條列（`- 輸入 → 預期結果`）。
- 需要網路或外部服務的條目，標題標註 `〔需網路〕`。
- Given、When、Then 有多個條件或結果時，用子項列出。
- 只能由人判斷的部分（例如 AI 的理由是否合理），在通過條件中明確寫出由誰判斷、看什麼。

#### AC-<slug>-<重點>：<標題>

- Given：前置條件
- When：執行的動作
- Then：預期結果
- 通過條件：…
