# web app 原型：設計與待決事項

## 1. 用途與生命週期

本文件記錄 web app 原型（`prototypes/job-table/`）已定案的介面設計，以及還沒決定的事項。

- 這是過渡文件，只存在於「原型定案 → 功能文件改完」這段期間。
  - 已定案的設計，之後寫成各功能文件的使用者故事。
  - 各功能文件改完後，刪除本文件。
- 原型用假資料模擬，開啟方式見 [prototypes/README.md](../../prototypes/README.md)。
- 功能文件還沒改之前，各功能的現有規則仍以功能文件為準；本文件只記錄介面要往哪裡改。

## 2. 背景

[決策紀錄：介面形式選型](decisions/interface-selection.md)定下本機 web app 與分階段推進。第 2 階段開工前，先用假資料做一個操作起來像真的原型，確認介面符合需求，再修改產品文件：

- 各功能擁有的介面，彼此怎麼拼成同一個頁面，只看文件不容易判斷。
- 原型可以直接操作，比在文件裡描述更快發現缺漏。

## 3. 已定案的設計

每項寫明之後歸哪個功能的使用者故事。上層功能對底層頁面的擴充，依[功能文件的結構](../conventions/documentation.md#功能文件的結構)，寫成上層自己的故事。

### 3.1 共通

- web app 不獨立成一個功能：各功能擁有自己那一段介面，就像現在各功能擁有自己的 CLI 與查詢。
- 外殼（啟動 web app、版面、導覽、框架）屬技術問題，不寫進功能文件。
- 頁面依使用者想怎麼查詢來切，不依功能切。目前有三個分頁：
  - 職缺表：瀏覽、篩選、評分累積下來的職缺
  - 抓取：輸入條件抓取職缺，預覽這次抓到的職缺，決定要不要存入
  - 設定：編輯偏好、經歷、提示詞模板的版本，用試跑清單試跑（見 [§3.3](#33-job-auto-scoring)）
- 不做詳情頁，改成在表格上點一列展開。
- 單人、只跑在本機，符合[非目標](overview.md#非目標)。
- 從介面觸發抓取與評分提前到這次一起做，原本排在第 5 階段（[決策紀錄：介面形式選型](decisions/interface-selection.md)）：
  - 抓完就能在同一個介面評分，才省得下篩選的時間。
- 流程是抓取 → 預覽 → 存入 → 評分：評分從職缺資料庫讀職缺，還沒存入的職缺不能送去評分。
- 送去評分與加入試跑清單都從職缺表發起，抓取頁不能送去評分：
  - 抓取頁屬於 104-job-scraper。評分功能在抓取頁加上送去評分，[功能依賴](overview.md#功能依賴)會多出 `job-auto-scoring → 104-job-scraper`，之後每接一個新平台的爬蟲，評分都要再擴充一次。
  - 存入後跳到職缺表，再從職缺表送去評分（見 [§3.4](#34-104-job-scraper)）。
- 抓取、評分、試跑都是在伺服器上跑的作業：
  - 重新整理、切到別的分頁或關掉瀏覽器，作業都繼續跑；重新打開頁面時接回進度。
  - 同一時間只跑一個作業，試跑也算一個作業：例如評分中不能開始抓取或試跑，抓取中不能開始評分。
- 產品介面只有 web app，不再為 CLI 設計新的行為：
  - 讓 agent 操作還沒規劃，等規劃時再依需求設計介面，不預先保留 CLI。
  - 同一件事只有一個入口，不必維持兩套規則一致。
  - 功能改成網頁版時，在同一個故事裡拿掉對應的 CLI，任何時候都至少有一個能用的入口。例如抓取頁完成時，拿掉抓取的 CLI。
  - CLI 目前有、但網頁上不需要的功能，隨 CLI 一起拿掉：
    - [匯入過去抓好的 JSON](features/104-job-scraper.md#8-把過去抓好的-json-匯進來import)：不再產生新的 JSON，只剩過去的檔案用得到。
    - 爬蟲的互動模式：由抓取頁的條件表單取代。

### 3.2 job-database

職缺表：

- 一次列出全部符合條件的職缺，不分頁，顯示符合幾筆、共幾筆。
- 選欄位：可以勾選職缺欄位契約的欄位與首次、最後出現時間，預設只顯示精簡的幾欄。
- 點欄位標題排序，再點一次反向；沒有值的一律排在最後。
- 選好的欄位、篩選與排序記在瀏覽器，下次打開沿用；記不住時退回預設。
- 點一列展開，顯示完整的職缺欄位、工作內容、出現時間，以及職缺頁與公司頁的連結。

篩選，加在 [query 故事](features/job-database.md#5-查出累積下來的職缺query)：

- 關鍵字：比對職缺名稱、公司名稱、工作內容、電腦專長。
- 地區：比對 `地區` 是否包含輸入的文字，可以篩到縣市或行政區，例如 `台北市`、`內湖`。
  - 不和關鍵字篩選合併：合併的話，輸入「台北」也會篩到工作內容提到台北的職缺。
  - `地區` 合併了縣市行政區與街道地址，所以也會比對到街道名稱；之後拆成兩欄時，改成只比對縣市行政區（見 [TODO.md](../../TODO.md#拆開地區欄位)）。
- 關鍵字與地區用同一套比對規則：
  - 多個關鍵字或多個地名以逗號分隔，符合任一個就算，和抓取條件的關鍵字寫法一致。
  - 不分大小寫。
  - 「臺」視為「台」，因為 104 的地區一律寫「台」。

不另外取出縣市，職缺表也沒有「縣市」欄，要看地點時選「地區」欄。

剛存入的職缺：

- 職缺表可以只列出指定的幾筆職缺，顯示「剛存入的 N 筆」：抓取頁存入後，帶著這次存入的職缺代碼清單跳過來（見 [§3.4](#34-104-job-scraper)）。
- 這是暫時的篩選，不做「挑選過去任何一次寫入」的篩選：職缺表才不依賴執行紀錄，執行紀錄的去留還沒決定（見 [§3.4](#34-104-job-scraper)）。
- 顯示「剛存入的 N 筆」時，其他篩選暫停：
  - 關鍵字、地區、總分範圍、評分狀態的欄位反灰、不能調整，「清除篩選」也不能用，職缺表只列出這 N 筆。
  - 關掉標籤後回到原本的篩選，才能再調整；記在瀏覽器的篩選不受影響。
  - 不和其他篩選疊加：疊加的話，標籤寫 N 筆，表格卻可能只列出幾筆，例如設了總分範圍時，還沒評分的職缺一筆都不剩。

職缺表有「還原預設檢視」按鈕：欄位、篩選與排序回到預設。顯示「剛存入的 N 筆」時，只還原欄位與排序。

手動新增一筆職缺（例如其他平台的職缺）延後，和職缺欄位契約的平台中立化一起規劃，已記在 [TODO.md](../../TODO.md#把職缺欄位契約改成平台中立)。

改版時保留資料，寫成 job-database 的非功能需求：

- 資料庫結構改版時，保留既有的職缺與執行紀錄；改版失敗時可以還原，資料不會遺失。
- job-database 用來累積歷史，資料不遺失是它自己的承諾；過去靠爬蟲的 JSON 重新匯入補著，不再輸出 JSON 後改由它自己保證。
- 先備份資料庫再遷移，是技術設計的做法，不寫進功能文件。

### 3.3 job-auto-scoring

評分資料庫併回自動評分：

- job-score-database 併進 job-auto-scoring，產品上只有一個評分功能；程式模組維持分開，評分紀錄的保存與自動評分仍是不同的模組。
  - 當初拆開的唯一理由是手動評分。拿掉手動評分後，評分資料庫單獨存在時沒有任何方式產生評分，沒有對應的使用者問題。
  - 評分紀錄的欄位、代表的評分、依分數查詢都歸 job-auto-scoring。
  - 拿掉只為手動評分存在的規則：評分的職缺不必先寫進職缺資料庫、`評分來源`、手動與自動評分並存。評分的職缺都來自職缺資料庫，不會有只有評分、沒有職缺資料的評分紀錄。
- 拿掉手動評分：
  - 包含[手動記錄評分](features/job-score-database.md#5-手動記錄評分manual)的故事，以及網頁上的填分表單。
  - 手動評分唯一想到的用處是比對 AI 和自己的判斷，改由第 3 階段的標記處理（見 [§3.5](#35-延到第-3-階段的標記)）。

職缺表：

- 多了總分、淘汰、評語、評分時間、四個維度的分數、供應商、模型欄。
- 表格上的分數一律用代表的評分，也就是最新的一筆。
- 預設依總分由高到低排序，沒評分的排在最後。
- 篩選：
  - 總分範圍：設了範圍時，排除沒有總分的職缺，也就是被淘汰與還沒評分的職缺。
  - 評分狀態：全部、未淘汰、淘汰、未評分。「未淘汰」只含評過而且沒被淘汰的職缺，不含未評分。

展開的列：

- 目前的評分：總分、淘汰、評語、評分時間。
- 評分明細：四個維度的分數與理由、未知維度；被淘汰時改顯示淘汰原因。
- 所有評分紀錄，由新到舊：
  - 點其中一筆，評分與評分明細（包括評分依據）換成那一筆，並標示「檢視中，不是目前的評分」，可以回到目前的評分。
  - 表格那一列仍然顯示最新的一筆。
- 評分依據，預設收合，分頁切換：
  - 評分時用的偏好：這筆評分紀錄指向的版本
  - 評分時用的經歷：這筆評分紀錄指向的版本
  - 這筆職缺實際送給 AI 的提示詞：由送評時的職缺內容快照與三份設定的版本組回來；被淘汰的職缺沒有呼叫 AI，沒有提示詞
  - 沒有記錄依據的舊評分，顯示「這筆評分沒有記錄依據」。

設定的保存：

- 偏好、經歷、提示詞模板都存在職缺資料庫，每次儲存留下一個版本：
  - 每個版本有名稱與描述，儲存時填寫，名稱必填，回頭找以前的設定比較容易。之後可以修改名稱與描述，版本的內容不能改。
  - 版本只新增、不刪除，評分紀錄指向的版本永遠查得到。
- 目前設定是其中一個版本，不一定是最新的一版：
  - 可以把任何一版套用成目前設定，套用不新增版本。回到舊的設定時，版本紀錄不會多出內容重複的版本。
  - 不另外記「什麼時候套用哪一版」：評分紀錄已經記下當時用的版本，每筆分數的依據都追得到。取捨：版本紀錄看不出每一版實際用過哪段時間。
- 第一版：偏好與經歷用專案的預設範例，提示詞模板用專案的預設模板。
  - 不從 `profile/` 的檔案匯入，也不再讀 `profile/` 的檔案，一律以資料庫裡的設定為準。
- 程式固定的部分：三個 AI 維度的名稱與個數、回應格式，由程式以 JSON schema 要求 AI 回應。
  - 模板只能改 AI 怎麼判斷，要加減維度仍要改程式。
  - [錨點描述](features/job-auto-scoring.md#425-ai-維度的錨點描述)與[提示詞設計](features/job-auto-scoring.md#428-提示詞設計)的規則（只根據提供的資料判斷、不准猜分數等），從固定的業務規則改成預設模板的內容。

評分依據的保存：

- 每筆評分紀錄記下：
  - 用到的偏好、經歷、提示詞模板各是哪一版
  - 送評時的職缺內容快照：影響評分的欄位，也就是送進 AI 的職缺名稱、公司名稱、產業類別、電腦專長、科系要求、工作內容，加上計算薪資分數與淘汰用的薪資待遇、薪資下限、薪資上限。被淘汰的職缺也存。
- 要存快照，是因為職缺資料庫只保留每筆職缺的最新一版：104 改過內容後，只靠設定版本組不回當時送給 AI 的提示詞。
- 不存 AI 的原始回應。
- 改版時保留資料，寫成 job-auto-scoring 自己的非功能需求：資料庫結構改版時，保留評分紀錄與設定版本，失敗時可以還原。job-database 不知道評分存在，不替評分的資料保證。

設定編輯與試跑：

- 在網頁上編輯偏好、經歷、提示詞模板，編輯區一開始載入目前設定：
  - 點版本紀錄的任何一版，把那一版載入編輯區，可以直接套用，或以它為底修改；編輯區比較大，也比較好讀。編輯區有還沒儲存的修改時，先確認才蓋掉。
  - 「還原預設」把預設範例或預設模板放進編輯區，算是一次修改。
  - 編輯區的內容只給試跑用，儲存或套用前不動目前設定。不直接改目前設定來試跑，因為試完不好要自己改回去；忘了改回去，下次正式評分就會用到實驗中的設定。
  - 瀏覽器記住編輯區，直到套用、儲存或捨棄修改；記不住時退回目前設定。
- 同一個編輯畫面有「試跑」與一個主按鈕，主按鈕依編輯區的狀態：
  - 和載入的那一版相比有修改：「儲存並套用」，填名稱與描述後存成新版本，並改用這一版。只要有修改就新增版本，即使內容剛好和其他版本相同，操作起來才不會疑惑怎麼變成套用別的版本。
  - 沒有修改、載入的不是目前設定：「套用第 N 版」，只換目前設定，不新增版本。
  - 沒有修改、載入的就是目前設定：停用，顯示「已是目前設定」。
  - 試跑：用三份編輯區的內容評試跑清單的職缺，看新設定對這些職缺的判斷，不影響正式分數。
  - 儲存或套用都不自動重評。評分在開始時讀一次目前設定，評分中換了設定只影響之後的評分。
- 試跑清單：
  - 在職缺表勾選職缺後按「加入試跑清單」，已在清單裡的不重複加入。
  - 清單和職缺表的勾選分開，記在瀏覽器：勾選在改篩選、送去評分後會清掉，清單不會，調整設定時可以反覆拿同一批職缺比較，開發者調整提示詞也有一批固定的職缺。
  - 設定頁用一張表列出清單的職缺：職缺名稱、公司名稱、目前總分，可以排序、移除單筆或清空；照表格目前的順序試跑。
  - 試跑結果加在同一張表上：試跑總分、和目前總分的差距、狀態；點一列並排比較。
  - 試跑後又改了清單或編輯區的內容，表上標示結果是改之前的，按一次試跑才會用現在的清單與內容。
- 試跑的結果不存：
  - 和目前的評分並排比較：總分、各維度的分數與理由、評語。
  - 離開頁面或重新整理就不見；代表的評分與評分紀錄的規則都不動。
- 試跑送出前的確認與可以停止，都和正式評分相同（見下面的送去評分、評分中與評完）。
- 檢查：
  - 模板整份都能改。儲存與試跑前檢查：缺少 SYSTEM／USER 標記或有不認得的變數時拒絕；少了職缺或個人資料的變數時提醒，但允許。
  - 偏好的格式照現有的[驗證規則](features/job-auto-scoring.md#422-preferencesyaml-欄位字典)，儲存、試跑、送去評分前都檢查，有錯時拒絕並顯示原因，避免產生錯誤的評分。
- 開發者調整提示詞也用試跑，不另外開測試用的資料庫。

勾選：

- 職缺表的每一列都可以勾選，勾選的職缺用來送去評分或加入試跑清單。
- 有「全選」與「取消全選」，全選是指目前篩選後顯示的所有列。
- 改篩選時清掉勾選，送出的職缺一定是看得到的。
- 送去評分時清掉勾選，勾選的職缺交給評分作業，不會不小心再送一次。

送去評分：

- 只從職缺表勾選職缺送出（見 [§3.1](#31-共通)）。
- 送出前確認，寫出：
  - 勾選了幾筆，其中幾筆已評過
  - 「包含已評過的職缺（重評）」勾選框，預設不勾：不勾時只評還沒評過的職缺；勾了時已評過的職缺也評，各新增一筆評分紀錄
  - 將評幾筆，其中幾筆符合淘汰條件、不呼叫 AI
  - 用哪個供應商與模型，模型可以在這裡選
- 不論怎麼篩選都可以全選送出：想評完所有還沒評過的職缺時，全選後送出即可，不必另外提供按鈕；重評預設不勾，全選時也不會不小心重評。
- 照表格目前的顯示順序評，中途停止時，排在前面的職缺已評完。
- 不做快取：要不要重評已評過的職缺，由使用者在確認視窗決定（見[決策紀錄：自動評分不做快取](decisions/no-score-cache.md)）。
- 開始前的錯誤在確認視窗就檢查，有錯時顯示原因、不能送出，一筆都不評：
  - 缺少 API key，或指定了不支援的供應商，而且有需要呼叫 AI 的職缺
  - 偏好的格式錯誤
  - 目前設定的偏好或經歷還是預設範例：用範例評出的分數沒有意義，還會成為代表的評分。試跑不擋。

評分中與評完：

- 評完一筆就更新那一列，列上標出排隊中、評分中、評分失敗。
- 表格的列與順序固定，只更新分數與狀態；改篩選、改排序或重新整理時才重新排列。
- 頁首顯示整體進度，切到別的分頁也繼續跑。
- 可以停止：評完目前這一筆就不再評，已評完的保留。評分會花錢，選錯模型時更需要停。
- 評完顯示摘要：成功、淘汰、失敗各幾筆。
- 評分失敗的職缺照現有規則不寫入：
  - 失敗的列上看得到失敗原因，重新整理後失敗標示就消失。
  - 可以再勾選重評。

### 3.4 104-job-scraper

- 抓取分頁的條件沿用現有的搜尋條件（見 [104-job-scraper 的 CLI](features/104-job-scraper.md#1021-cli)）：
  - 關鍵字，多個以逗號分隔
  - 縣市，單選，不選代表全台灣
  - 每個關鍵字抓幾頁
  - 職缺性質
- 記住上次用的條件。
- 抓取中：
  - 顯示進度，例如搜尋到第幾頁、取職缺內容到第幾筆。
  - 可以停止：不再發出新的請求，提早結束，預覽已經取完內容的職缺。
  - 職缺不逐筆出現，抓完或停止後一次列出。
- 預覽：
  - 這次抓到的職缺列在抓取頁，只顯示職缺欄位契約的欄位，並標出資料庫裡還沒有的職缺。
  - 選欄位、排序、展開的操作和職缺表相同；選的欄位與排序另外記在瀏覽器，不影響職缺表。
  - 不顯示評分欄，也不能送去評分：評分功能不擴充抓取頁（見 [§3.1](#31-共通)）。
- 預覽後整批存入或整批捨棄，不能只存入其中幾筆：
  - 想擋掉的情況有三種：搜尋條件下錯整批不要、一批裡混了無關職缺、只是想先看看抓到什麼。
  - 整批處理的規則單純，存入的職缺都有完整的出現紀錄。
  - 取捨：捨棄的職缺不會進入之後的趨勢分析，也無法抽查誤殺。
- 存入的規則和現在抓完寫入資料庫相同（見 [store 故事](features/104-job-scraper.md#7-抓完的職缺自動存進職缺資料庫store)），另外：
  - 執行紀錄的 `來源` 維持 `爬蟲`；舊資料的 `匯入` 照舊代表匯入 JSON。
  - `執行時間` 用抓完或停止的時間，也就是實際看到這些職缺的時候，不用按下存入的時間。
  - 中途停止的抓取，`頁數` 仍記要求的頁數。執行紀錄照舊寫入，不再為它加欄位或介面；等趨勢分析規劃時，再決定執行紀錄的去留（見 [TODO.md](../../TODO.md#做趨勢圖表)）。
- 存入後跳到職缺表，顯示「剛存入的 N 筆」（見 [§3.2](#32-job-database)），要評分時從職缺表送出。
- 沒存入的抓取結果留在伺服器，直到存入、捨棄或重新抓取：重新整理或關掉瀏覽器後回到抓取頁仍看得到，web app 關閉才會消失。
- 抓取頁完成時，拿掉抓取的 CLI（見 [§3.1](#31-共通)），抓完直接寫入資料庫的流程跟著消失。
- 不再輸出檔案：
  - CSV 與 JSON 都拿掉，用 Excel 開的需求已由職缺表取代。
  - 資料庫結構改版時，不再靠 JSON 重新匯入，改由 job-database 與 job-auto-scoring 各自保留資料（見 [§3.2](#32-job-database)、[§3.3](#33-job-auto-scoring)）。
  - notebook 改讀資料庫或退場，去留已記在 [TODO.md](../../TODO.md#決定-notebook-的去留)。
  - 「只輸出檔案、不寫入資料庫」的選項跟著拿掉。

## 5. 原型的簡化

以下是原型為了模擬而簡化的地方，實作時照各功能文件現有的規則，不是設計的改變：

- 已存在的職缺再次抓到時，原型只更新最後出現時間，也沒有顯示執行紀錄；實作照 [job-database 的寫入規則](features/job-database.md#421-寫入規則)。
- 淘汰判斷只比月薪上限與底線；實作照[硬性淘汰規則](features/job-auto-scoring.md#521-硬性淘汰規則)與[薪資換算](features/job-auto-scoring.md#426-薪資換算與計分)。
- 提示詞模板省略了錨點描述。
- 維度分數、評語、評分失敗與失敗原因都是隨機產生的。
- 抓取、評分、試跑都跑在瀏覽器裡：重新整理後不會接回進度，抓取結果、評分、儲存的設定版本與套用的版本也會消失。只有選好的欄位、篩選、排序、抓取條件、設定編輯區的內容與試跑清單記在瀏覽器。
- 偏好的格式只做簡化的檢查：必要的鍵、月薪是正整數、權重是數字且加總為 1；實作照 [preferences.yaml 欄位字典](features/job-auto-scoring.md#422-preferencesyaml-欄位字典)的驗證規則。
- 缺少 API key 用頁首的「模擬沒有 API key」開關示範。
