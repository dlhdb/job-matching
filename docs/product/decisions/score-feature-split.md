# 拆分評分資料庫與自動評分

## 決策背景與問題

原本的 job-scoring 同時負責兩件事：怎麼替職缺評分，以及評分怎麼保存、查詢。

使用者要能自己手動填分：

- 手動評分和 AI 評分寫的是同一種東西（是否淘汰、總分、評語），差別只在怎麼產生。
- 如果保存與查詢留在 job-scoring，手動評分就得依賴一個以 AI 為主的功能，或是另外寫一套保存與查詢。

問題是：功能邊界要怎麼切，才能讓評分的產生方式可以增加，而保存與查詢不必跟著改？

## 考慮過的替代方案

- 不拆，維持一個功能：
  - 手動評分要寫進 job-scoring，但它和 AI、提示詞、快取都無關。
  - 功能文件已經超過一千行，加上手動評分後更難讀。
- 依 AI／非 AI 切分（AI 評分一個功能，硬性淘汰、薪資計分與保存另一個）：
  - 硬性淘汰、薪資計分與 AI 評分共用同一套評分流程與結果格式，切開後兩邊都要知道對方的結果長什麼樣子。
  - 切的是實作方式，不是使用者能單獨得到的價值。
- 評分結果格式（各維度的分數與理由、淘汰原因、未知維度）由評分資料庫擁有：
  - 這些是自動評分的邏輯，手動填分時不會有。
  - 資料庫要規定有哪些維度，就得反過來引用自動評分的維度定義，形成雙向依賴。
- 評分資料庫保留一個原樣保存、不解析的明細欄位（或叫「備註」），讓自動評分把評分結果放進去：
  - 手動評分用不到，等於在底層先替上層留了欄位。
  - 叫「備註」時會和 `評語` 分不清，而且自動評分放的是給程式讀的 JSON，不是給人看的自由文字。
- 評分資料庫一開始就規劃手動與自動並存的欄位（評分來源、供應商、模型）：
  - 等於在底層預先為上層設計，底層反過來依賴上層。
  - 還沒有自動評分時，這些欄位沒有意義。
- 評分來源存成 `auto_<供應商>_<模型>` 一個字串：
  - 篩選「所有自動評分」或「某個供應商」時，要做字串比對。
  - 模型名稱本身可能含 `_` 或 `-`，拆回去時容易出錯。
- 已讀、想投、略過等標記與評分共用同一份契約：
  - 標記是狀態，不是分數，用途是分析自己實際被哪些職缺吸引（UP-05），不是排序。
  - 兩者到查詢端（例如瀏覽頁）才合在一起。

## 最終決策

- 拆成兩個功能，依賴方向是 `job-auto-scoring → job-score-database → job-database`：
  - [job-score-database](../features/job-score-database.md)（評分資料庫）：保存與查詢評分紀錄。
  - [job-auto-scoring](../features/job-auto-scoring.md)（職缺自動評分）：原本的評分邏輯。
- 功能漸進疊加：規劃底層功能時，假設上層功能不存在。
  - 評分資料庫只定義人工就填得出來的基本欄位：`職缺代碼`、`評分時間`、`淘汰`、`總分`、`評語`。
  - 自動評分需要的欄位與規則寫在自動評分的功能文件：
    - 評分明細（各維度的分數與理由、淘汰原因）、`供應商`、`模型`
    - 評分來源（`manual`／`auto`）
    - 手動與自動評分並存、保留歷史
- 評分來源用一個欄位存 `manual`／`auto`，`供應商`、`模型` 各自一欄。
- 標記不共用評分紀錄，由之後的標記功能另外保存（見 [TODO.md](../../../TODO.md#標記職缺)）。
