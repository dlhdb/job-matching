# 0003 功能不再分組，ID 用英文簡稱

## 決策背景與問題

專案總覽原本把功能歸在五項「核心技術」底下，功能 ID 的第一個數字就是核心技術編號（例如職缺評分是 `F1-01`）。五項核心技術裡有四項底下只有一個功能，兩層在講同一件事，卻讓 ID、檔名、開發流程、名詞定義與功能文件表頭都多了一個要維護的概念。問題是功能要不要分組，以及拿掉分組後 ID 怎麼取。

## 考慮過的替代方案

- 保留核心技術分組（原本的結構）：多數分組底下只有一個功能，定義、對應的使用者問題與「現況」都在分組和功能兩層重複。只有「從求職平台獲取職缺」底下真的有多個功能，不值得為它保留一整層。
- 改成不分組的流水號（例如 `F01`、`F02`）：號碼本身不帶資訊，讀到 ID 還是要回頭查功能清單才知道是哪個功能，也和 FR／AC 不用流水號的規則不一致。
- 保留既有 ID，只移除核心技術章節：改動最少，但舊 ID 仍然暗示分組，新功能若改用新格式，兩種 ID 會並存。

## 最終決策

- 功能是系統中一個獨立且可交付的大型功能模組，不再歸屬於任何分組。功能的定義、解決的使用者問題與現況，直接寫在 [專案總覽的功能清單](../README.md#功能清單)。
- 功能 ID 比照 FR／AC，用英文簡短描述（kebab-case，例如 `job-scoring`），也是功能文件的檔名 `<功能 ID>.md`。規則見 [documentation.md「功能文件的結構」](../conventions/documentation.md#功能文件的結構)。
- 104 爬蟲與職缺資料庫仍是兩個獨立功能，因為各自可以單獨交付。
- 影響的文件：[docs/README.md](../README.md)、[feature_template.md](../features/feature_template.md)、所有功能文件的檔名與表頭，以及引用功能 ID 的 [CLAUDE.md](../../CLAUDE.md)、[README.md](../../README.md)、[TODO.md](../../TODO.md)。
