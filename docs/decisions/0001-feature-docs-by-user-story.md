# 0001 功能文件以使用者故事分章

## 決策背景與問題

一份功能文件同時放需求、設計與驗收。實作或修改時，要能只讀到一個範圍，又能確認每條需求都有驗收涵蓋。問題是章節要依什麼切分。

## 考慮過的替代方案

- **需求、設計、驗收各切一章**（最早的結構）：同一件事的需求、規則與驗收散在三章，要靠連結互指。改一件事要在三章之間來回，也不容易確認哪些需求還沒有驗收。
- **依系統能力分章**（上一版，F1-01 曾切成 profile、score、batch、store）：同一件事已經集中在一章，但系統能力是從實作角度切的，太抽象，讀章名看不出使用者能做到什麼。「使用情境」另外列在一節，和章節之間沒有對應，看不出哪個情境由哪一章實現、哪個還沒做。
- **一章一個故事，全部保留**：原本的每條使用情境各自成章。「單筆失敗不中斷整批」這類附帶條件也會變成一章，章內只有一條需求。多個故事共用的設計（評分流程、維度）只能全部上提到共用設計，共用設計會膨脹。

## 最終決策

- 一章一個使用者故事，每個故事是一個可以單獨交付的價值切片，章名寫使用者能做到的事。
- 附帶條件的小故事寫成所屬故事的 FR；設計放在最先用到它的故事，後面的故事用連結引用。
- 規則見 [conventions.md「功能文件的結構」](../conventions.md#功能文件的結構)，骨架見 [feature_template.md](../features/feature_template.md)。
