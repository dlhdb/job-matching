# web app 框架選型：React + FastAPI

## 決策背景與問題

產品介面改成本機 web app（見[決策紀錄：介面形式選型](../product/interface-selection.md)），第 2 階段要做出職缺表、抓取頁與設定頁。要決定：

- 用哪一套框架。
- 規則放在伺服器還是瀏覽器。

頁面要做到的事，需求見 [job-database](../../product/features/job-database.md)、[104-job-scraper](../../product/features/104-job-scraper.md)、[job-auto-scoring](../../product/features/job-auto-scoring.md)：

- 職缺表一次列出上百到上千筆職缺，不分頁，可以選欄位、排序、篩選、點一列展開、勾選。
- 抓取、評分、試跑是在伺服器上跑的作業：
  - 關掉瀏覽器也繼續跑
  - 重新打開頁面時接回進度
  - 評分中逐列更新狀態
- 很多狀態只存在瀏覽器，而且牽動頁面的好幾個地方：
  - 記在瀏覽器的檢視、抓取條件、設定的編輯區與試跑清單，瀏覽器不允許保存時退回預設
  - 勾選在改篩選時清掉
  - 評分中列的順序固定
  - 設定頁的主按鈕依編輯區和載入的版本比對，有三種狀態
  - 試跑結果只留在打開的頁面
- 設定頁邊編輯邊檢查偏好與提示詞模板，儲存、套用與評分前也用同一套規則檢查。

限制：

- 單人、只跑在本機（見[非目標](../../product/overview.md#非目標)），不需要處理多人同時使用、登入或部署。
- 後端的業務規則已經是 Python：偏好以 Pydantic 驗證，淘汰與薪資規則在 `job_scoring`，測試用 pytest（見 [development.md](../../conventions/development.md#測試)）。
- 第 2 階段開工前已經有一份可操作的原型（`prototypes/job-table/`）：單一 HTML 檔加原生 JavaScript，資料是假的，互動都在瀏覽器端完成。

## 考慮過的替代方案

- FastAPI + Jinja2 + HTMX（由伺服器產生 HTML，元素被操作時向伺服器要一段 HTML 替換頁面的一部分）：
  - 優點：只有 Python，不需要前端 build，程式碼量最少。
  - 擅長「送出請求 → 伺服器處理 → 顯示結果」的頁面，但上面列的瀏覽器端狀態都要跳出 HTMX 的模式，另外手寫原生 JavaScript。
  - 這些零散的 JavaScript 沒有結構，也沒有單元測試，互動越多越難維護。
- FastAPI JSON API + 沿用原型的原生 JavaScript：
  - 優點：原型已經做出幾乎所有互動，最快做到和原型一樣。
  - 原型是一份約 1700 行、沒有型別檢查也沒有測試工具的 JavaScript，繼續長大後難以維護。
- Streamlit：
  - 優點：做得最快。
  - 每次互動整份腳本重跑，上百筆職缺的逐筆判讀會卡。
  - 點一列展開、評分中維持列的順序、記在瀏覽器的狀態與背景作業，都要繞過框架的執行模型。
- Svelte 或 Vue：
  - 分工和採用的方案相同。
  - Svelte 的程式碼更精簡。
  - 表格、圖表函式庫的選擇比 React 少；之後的標記職缺與趨勢圖表互動更多，生態大的比較好接。

## 最終決策

- 前端用 React + TypeScript，以 Vite 開發與 build。
- 後端用 FastAPI 提供 JSON API，並提供 build 好的前端檔案。
- 前端 build 的產出不進版控，啟動 web app 前先 build。
- 選前端框架的原因：
  - 頁面的難處在瀏覽器端的狀態，不在伺服器處理：
    - [決策背景](#決策背景與問題)列出的狀態都只存在瀏覽器，又互相牽動。
    - 前端框架把它們放在元件的狀態裡，依狀態算出畫面，不必手動同步頁面上的好幾個地方。
  - 職缺表、抓取的預覽、試跑清單是同一種表格（選欄位、排序、展開），做成一個元件共用，規則只寫一份。
  - 看資料的規則寫成 TypeScript 純函式，有型別檢查，也能用 Vitest 做和 pytest 一樣細的單元測試。
  - 原型的互動本來就在瀏覽器端完成，搬到前端框架時的落差最小。
- 選 React 的原因：生態最大，表格與圖表函式庫最多；之後的標記職缺與趨勢圖表互動更多，最好接。
- 選 FastAPI 的原因：
  - 以型別標註與 Pydantic 定義請求與回應，和後端既有的 Pydantic 模型一致。
  - 會從這些定義產生 OpenAPI 規格，前端的 API 型別可以由它產生，前後端的欄位不會各寫一份。
  - 內建供 pytest 使用的測試 client。
- 規則依性質分在前後端：
  - 前端：看資料的方式，寫成純函式用 Vitest 測。
    - 包括篩選、排序、選欄位、展開、勾選與記在瀏覽器的狀態，都對已經載入瀏覽器的資料操作。
    - 職缺表本來就一次列出全部，上千筆職缺連同工作內容在本機傳輸沒有負擔，在前端做反應最即時。
  - 後端：評分作業或資料庫也要用的規則，只寫一份，用 pytest 測。
    - 設定檢查：
      - 不只是編輯時的提示，也是儲存、套用、送去評分前的檢查。
      - 編輯區的即時檢查呼叫同一個 API，前端不另寫一份。
    - 確認視窗中「符合淘汰條件」的筆數：和評分用同一份硬性淘汰規則。
    - 代表的評分、評分紀錄、設定的版本：資料庫查詢。
    - 抓取、存入、評分、試跑：伺服器上的作業。
- 作業的進度由頁面定時向伺服器詢問，不用 WebSocket：單人本機使用，輪詢的成本可以忽略，實作也最單純。
- 付出的代價：
  - 多一套 Node.js 工具鏈（npm、Vite），依賴、測試與型別檢查都是 Python、TypeScript 各一套。
  - 啟動前要先 build，開發時另外跑 Vite 的開發伺服器。
  - API 的請求與回應要定義成 JSON，程式碼量比伺服器直接產生 HTML 多。
- 前後端串起來才看得到的行為（記在瀏覽器、確認視窗、作業中逐列更新等），以 Playwright 在真的瀏覽器中驗證。
