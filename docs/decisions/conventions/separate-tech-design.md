# 功能文件與技術設計分開維護

## 決策背景與問題

原本一份功能文件同時放需求、規則、實作方式與驗收的測試指令。問題：

- 讀者不同：
  - PM、設計師、架構師要看的是為什麼做、做什麼。
  - 模組佈局、SDK 的參數、結束碼、測試 fixture 只有工程師需要。
  - 兩者混在一起，非工程師要跳過大量看不懂的內容。例如 job-scoring 約一半的篇幅是實作細節。
- 變動頻率不同：
  - 需求與業務規則相對穩定。
  - 實作方式在重構時就會改。
  - 放在同一份文件，每次重構都要改動 PM 也會讀的文件。
- 工程師另外需要系統的整體輪廓：
  - 讀程式碼可以拼湊出來，但要花很多時間。
  - 設計散落在各個使用者故事裡，看不出元件之間怎麼分工。

## 考慮過的替代方案

- 全部留在功能文件，只要求設計小節寫得精簡：讀者混雜與變動頻率不同的問題仍在，只是程度較輕。
- 技術設計不寫文件，只靠程式碼與 docstring：
  - 工程師要讀完程式碼才拼得出系統輪廓，認知負擔高。
  - 外部系統的坑、設計理由等程式碼講不出來的事沒有地方放。
- 技術設計依使用者故事分章，與功能文件一章對一章：
  - 容易檢查每個故事是否都有設計，但同一個元件（資料表、LLM 抽象層）會散在多章，看不出整體。
  - 核對故事是否完成的需求，改由依故事分組的「驗收對照」滿足。
- 技術設計併進 [architecture.md](../../tech/architecture.md)：
  - architecture.md 是跨功能的總覽，加入各功能的細節後會過長。
  - 修改單一功能時要在大檔案中找對應的段落。
- 功能文件在標頭與相關段落連到技術設計，方便跳轉：
  - 功能文件因此依賴實作方式，技術設計改寫或重新分章時，功能文件也要跟著改。
  - 兩份文件檔名相同，工程師依功能 ID 就找得到技術設計。

## 最終決策

- 一個功能兩份文件，檔名都是 `<功能 ID>.md`：
  - 功能文件 `docs/product/features/`：為什麼做、做什麼，讀者是 PM、設計師、架構師與工程師。
  - 技術設計 `docs/tech/tech-design/`：怎麼做，讀者是工程師。
- 分界判準：「改掉這段，PM 或設計師需要知道嗎？」需要就寫功能文件。
- 依賴只有單向：技術設計引用功能文件，功能文件不引用技術設計，也不寫實作方式。
- 兩者所在的目錄分區見[決策紀錄：產品文件與技術文件分目錄](product-tech-directories.md)。
- 功能文件的故事章節改為需求／規則／驗收，「共用設計」改為「共用規則」。
- 技術設計：
  - 依元件分章，每章列出實現的 FR ID。
  - 只寫能建立整體認知，或程式碼講不出來的事，保持精簡。
  - 只描述已實作的現況，不標〔規劃中〕。
- 驗收拆成兩半，以 AC ID 對應：
  - 功能文件寫業務語言的 Given／When／Then 與通過條件。
  - 技術設計的「驗收對照」依故事分組，寫出驗證指令。
