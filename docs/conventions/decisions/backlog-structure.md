# 待辦的組織方式

## 決策背景與問題

待辦原本只有根目錄的一份 TODO.md，只收「已確認要做」的事，依 P0～P2 分組。用久了出現三個問題：

- 還沒決定要不要做的想法沒有地方放，對話結束後就消失。
- 少數項目的細節很長（例如 web app 第 2 階段要一起移除的清單），把索引撐得難以瀏覽。
- 看不出哪些項目已經有人在做，大項目跨好幾次對話做時，下一次對話接不上。

## 考慮過的替代方案

- 每項加上狀態欄位（待確認、待實作、實作中、待審查）：
  - 待確認：還沒決定要不要做的想法有獨立的「待評估」區，比混在 P0～P2 裡標狀態清楚；確定要做的項目，開工時要決定的事依功能開發流程在功能文件裡處理。
  - 待實作：幾乎每項都是，只是預設值；要等條件成立的已經有「條件」一行。
  - 待審查：commit-review 在 commit 後就審，審完才算做完，中間沒有等待審查的階段。
  - 實作中：功能的進度已經記在 overview 的功能清單，兩邊會對不上；文件、修正類的項目多半一次就做完。
  - 每次換狀態都要回來改 TODO.md，沒改到的狀態比沒有狀態更誤導。
- 還沒決定要不要做的想法混進 P0～P2：分組的前提是已經決定要做，想法放進去看起來像已經承諾；AI 讀到後也會當成既定方向。
- 分成 todo.md 與 ideas.md 兩份平行的清單：要去兩個地方看「有什麼事要做」，想法決定做時還要在兩份之間搬。
- 每項都開一個細節檔：短的項目三行就講完，多一個檔案只是多一層跳轉。

## 最終決策

- 待辦集中在 `backlog/`：`TODO.md` 是唯一的索引，細節太長的項目另開 `tasks/<名稱>.md`（確定要做）或 `ideas/<名稱>.md`（待評估），需要時才開。
- 索引分成 P0～P2 與「待評估」。P0～P2 依重要程度分組，不依做法是否已確定；大的取捨還沒決定時，以「決策」類型放進對應的組。
- 不加狀態欄位。只有已開工、一次做不完的項目加「進行中」一行，功能的進度仍以 overview 為準。
- 做完或決定不做才刪除項目與細節檔；不做的理由值得留下時寫成決策紀錄。
- 影響的文件：[backlog/TODO.md](../../../backlog/TODO.md)、[CLAUDE.md](../../../CLAUDE.md#待辦事項)、[README.md](../../../README.md#專案結構) 的專案結構。
