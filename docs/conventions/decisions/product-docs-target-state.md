# 產品文件寫應有的樣子，技術文件寫實作現況

## 決策背景與問題

原本的規則是「所有文件都描述系統的現況」，但其他規則要求規劃先於實作寫進產品文件：

- [撰寫與使用流程](../../README.md#撰寫與使用流程)要先改功能文件、清空待決問題，才開始實作。
- 功能文件以〔規劃中〕標出尚未實作的故事，overview 的圖以虛線畫出規劃中的功能與資料流。

兩邊互相衝突，每次規劃都卡在「產品文件要不要等實作完才改」。web app 第 2 階段要依原型大幅改寫功能文件，開工前要先定下來。

## 考慮過的替代方案

- 所有文件都寫現況，規劃另寫成過渡文件（例如 web app 原型設計）：
  - 規劃確定後，要讀兩份文件才知道產品要長什麼樣。
  - 待決問題、定稿這些步驟無法在功能文件裡進行，流程要整個改寫。
- 技術文件也寫規劃中的內容：
  - 技術方案在實作時常常改變，先寫進技術設計容易過時。
  - 實作前的技術方案已經有地方放：實作計畫或 commit 說明。
- 要拿掉的故事或規則保留原文，標〔規劃中移除〕，實作完成時再刪除：
  - 產品文件裡混著之後不會存在的內容，讀者要自己排除。
  - 要移除什麼是實作的待辦，記在 TODO.md 才能寫出要等哪個條件成立、追得到有沒有做完。
  - 目前能用的功能仍寫在 overview 的「現況」與技術設計，不必靠功能文件保留原文。

## 最終決策

- `product/`（overview、功能文件、產品決策紀錄）寫產品應有的樣子，規劃確定就更新，不等實作：
  - 尚未實作的部分，功能文件標〔規劃中〕，overview 的圖用虛線。
  - 例外：overview 功能清單的「狀態」與「現況」記錄實作進度。
- 要拿掉的故事或規則，規劃確定時直接刪除。實作時要一起移除的程式、測試與技術設計的段落記到 TODO.md。
- `tech/` 只描述已實作的現況，實作完成後才更新。
- 代價：刪掉的故事實作移除之前，技術設計的驗收對照中連到它的 AC 的連結會暫時失效，移除時一併刪掉。
- 影響的文件：
  - [documentation.md](../documentation.md#文件分區)的文件分區與內容
  - [_feature_template.md](../../product/features/_feature_template.md)的〔規劃中〕規則
  - [docs/README.md](../../README.md)的開頭與撰寫流程
  - CLAUDE.md 的文件描述原則
