# 文件撰寫慣例

這份只寫跨章、跨文件的規則，各章怎麼寫（例如驗收的寫法、技術設計不寫哪些內容）寫在範本的註解。只改文件時讀這份，加上要改的那類文件的範本：[_feature_template.md](../product/features/_feature_template.md)、[_tech_design_template.md](../tech/tech-design/_tech_design_template.md)，修改既有文件時也一樣。

## 文件分區

各區的內容見 [docs/README.md](../README.md)，理由見[決策紀錄：產品文件與技術文件分目錄](decisions/product-tech-directories.md)。依賴只有單向，實作改變時產品文件才不必跟著改：

- `tech/` 可以連到 `product/`，`product/` 不連到 `tech/`，包含 `tech/decisions/`。`conventions/` 兩邊都能連，兩邊也能連到它。
- 功能文件不寫實作方式，例如資料存在哪個資料庫、哪張表、由哪個模組寫入。提到資料庫時只寫「職缺資料庫」與保存了哪些資訊。例外是 CLI 參數說明中 `--db` 的預設值，那是使用者介面。
- 引用別的功能時，連到該功能的功能文件，引用它的業務規則與對外資料格式。

兩區描述的時間點不同，理由見[決策紀錄：產品文件寫應有的樣子，技術文件寫實作現況](decisions/product-docs-target-state.md)：

- `product/` 寫產品應有的樣子，規劃確定就更新，不等實作。尚未實作的部分，功能文件標[〔規劃中〕](#功能文件的結構)，overview 的圖用虛線。例外是 overview 功能清單的「狀態」與「現況」，記錄實作進度。
- `tech/` 只描述已實作的現況，實作完成後才更新。

`docs/` 只寫本專案的設計、技術選型與開發守則，這些沒有通用的標準答案，讀者是 AI agent、工程師、設計師與 PM。AI coding 的通用工作流（skill、hook、CLAUDE.md 的規則，換到別的專案也適用）不寫進 `docs/`：

- skill、hook：說明與設計理由寫在 `.claude/skills/<名稱>/README.md`。
- 只給某個 skill 用的 subagent：定義放在 `.claude/agents/`，說明與設計理由寫在該 skill 的 README。
- 只寫在 CLAUDE.md、沒有 skill 的規則：取捨寫成決策紀錄放在 `.claude/decisions/`，寫法同[決策紀錄](#決策紀錄)。

## 內容

- 文件一律使用繁體中文。
- 一個功能有功能文件與技術設計兩份，理由見[決策紀錄：功能文件與技術設計分開維護](decisions/separate-tech-design.md)。內容放哪一份，問「改掉這段，PM 或設計師需要知道嗎？」：
  - 需要：寫在功能文件，例如薪資換算規則、偏好檔欄位、CLI 參數、結果檔欄位。
  - 不需要：寫在技術設計，例如模組分工、資料表 schema、SDK 的限制、結束碼、測試資料。
- 文件寫決策的結果，不寫討論過程（例如「已與使用者確認…」）。決策的結果寫進對應的範圍、需求、規則或技術設計，有替代方案的取捨另外寫成[決策紀錄](#決策紀錄)。
- 只寫程式碼講不出來的事：規則與理由、外部系統的限制、資料契約。不抄函式簽名、完整的 API 呼叫，或逐行翻譯程式碼。
  - 流程寫每一步做什麼、讀進與產出哪些資料，不寫函式、變數名稱或例外類別，重構時文件才不必跟著改。
  - 功能文件的流程不寫模組名稱。技術設計寫到模組層級，函式名稱只在元件之間的約定需要時才寫。
- 跨功能的模組依賴、資料存放與技術選型寫在 [architecture.md](../tech/architecture.md)，只列總覽、細節連出去。功能的進入點、模組依賴、資料表或技術選型改變時一併更新。
- 程式碼不引用文件，見 [development.md](development.md#程式碼與文件的關係)。

## 功能文件的結構

為什麼以使用者故事分章見[決策紀錄：功能文件以使用者故事分章](decisions/feature-docs-by-user-story.md)。

- 範圍章直接列出範圍內的內容：
  - 使用者故事縮排成子清單列在這裡，故事清單只有這一份。非功能需求與共用規則各一項，冒號後寫章節裡有哪幾件事。
  - 範圍內與範圍外用同一種形狀：一項一件事，冒號後寫它的下落。
  - 範圍外只列實作者合理會以為包含、但其實不做的事：屬於相鄰功能的事、順手會做的下一步、刻意不採用的做法。不列出所有沒做的事，已寫在 overview [非目標](../product/overview.md#非目標)的事不重複列。
- 一個使用者故事一章，是一個可以單獨交付的價值切片：
  - 同一個故事的需求、規則與驗收放在同一章，不按「需求」「規則」「驗收」各切一章再互相連結。
  - 只是附帶條件的小故事（例如「單筆失敗不中斷整批」）寫成所屬故事的 FR，不單獨成章。
  - 角色只寫求職者或開發者。下游需要的資料格式寫在「輸入與輸出」的輸出，不寫成故事，也不點名是哪個功能。跨功能的關係只寫在 [overview 的功能依賴](../product/overview.md#功能依賴)與 architecture.md。
- 規則放在最先用到它的故事，後面的故事用連結引用，不重複寫。
- 功能漸進疊加。上層功能的需求動到底層功能時，改動該歸底層還是上層，判斷見[功能設計](../product/feature-design.md#上層的需求動到底層時)。歸上層的擴充寫成上層自己的使用者故事：
  - 擴充包括新增欄位、在底層的查詢多帶欄位。上層的故事寫明疊加了什麼、底層哪些規則不變，驗收與測試也放在上層。
  - 上層推翻底層既有的規則要盡量避免，理由見[功能設計](../product/feature-design.md#上層的需求動到底層時)。無法避免時，同樣寫在上層的故事，寫明推翻了底層哪條規則。
  - 底層的功能文件假設上層不存在，連措辭都不提上層：不在範圍外列上層、不在底層規則旁標上層造成的〔規劃中〕。
  - 底層的驗收只驗底層定義的內容，例如只驗基本欄位都在、不驗完整欄位清單，上層疊加欄位時底層的驗收才不會壞。
- 尚未實作的內容標〔規劃中〕，讀者才分得出哪些已經做得到：
  - 狀態為「待規劃」或「待實作」的新功能，整份文件都是規劃中，不必標記。
  - 既有功能修改時，〔規劃中〕標在故事層級：寫在故事章節的第一行，不寫進標題，狀態改變時錨點才不會跟著變。該故事內部不再逐條標記。
  - 既有故事或共用章節的規則被新故事改到時，在被改到的那一行標〔規劃中〕。
  - 故事整章改寫時，在故事層級標〔規劃中〕，舊內容直接改寫。
  - 要拿掉的故事或規則直接刪除，不保留原文。實作時要一起移除的程式、測試與技術設計的段落記到 [backlog/TODO.md](../../backlog/TODO.md)，實作完成前 overview 的「現況」仍照實際情況寫。
- 驗收預設驗同一章的需求：
  - 新故事對既有需求的改動，寫成新故事自己的 FR，既有故事的需求不動，改動的需求和驗收才會在同一章。
  - 驗收順帶驗到別章的需求時不另外標註。每條需求都要有驗收，逐章核對。

ID 一律用英文簡短描述，不用流水號，插入新條目時不必重編：

- 功能 ID 用 kebab-case（例如 `job-auto-scoring`），也是功能文件與技術設計的檔名，理由見[決策紀錄：功能不再分組，ID 用英文簡稱](../product/decisions/flat-feature-list.md)。
- FR 與 AC 是 `FR-<故事 slug>-<重點>`、`AC-<故事 slug>-<重點>`，非功能需求是 `NFR-<重點>`、`AC-nfr-<重點>`。
  - AC 驗的就是同名 FR 時沿用同一個重點名稱。故事只有一條需求時，可以省略 `-<重點>`。
  - AC 標題只寫 ID 與描述，不列出涵蓋哪些 FR，錨點才不會隨涵蓋清單改變。
  - 內文引用別章的需求時，寫出需求的內容並連到章節，例如「被淘汰的職缺不呼叫 AI（見 [§5](…)）」，不拿 FR ID 當連結文字。

## 技術設計的結構

- 依元件分章，不依使用者故事。每章列出它實現的 FR ID，需求才追得到設計。
- 只描述已實作的現況，不標〔規劃中〕：實作前的技術方案寫在實作計畫或 commit 說明，故事完成後再更新。
- 底層功能的技術設計不描述上層疊加的欄位與查詢，只寫「其他功能疊加的欄位見各功能的技術設計」。
- 技術設計是單一功能內的全貌，跨功能的全貌寫在 architecture.md。

## 決策紀錄

有替代方案、之後容易被重新提出的取捨，寫成決策紀錄，依性質放在：

- `product/decisions/`：業務規則、功能切分。
- `tech/decisions/`：技術選型與實作取捨。
- `conventions/decisions/`：本專案的文件與開發流程。
- `.claude/decisions/`：只寫在 CLAUDE.md 的 AI coding 規則，見[文件分區](#文件分區)。

- 檔名是描述決策目的的英文 kebab-case，例如 `database-selection.md`，不用流水號。引用時連結文字寫決策標題，例如「[決策紀錄：資料庫選型](…)」。
- 一份決策一個檔案，固定三節：
  1. 決策背景與問題：為什麼需要做這個決定。
  2. 考慮過的替代方案：每個方案一項，寫出未採用的原因。
  3. 最終決策：採用的做法，以及它影響到哪些文件。
- 決策改變時直接更新原檔，把原本的決策移到「考慮過的替代方案」並寫出不再採用的原因。
- 在做出該決策的文件中連到決策紀錄，理由不在兩處重複寫。

## 格式

- 一句話涉及多個概念、決策或情況時，改成條列，一個概念一項。
- 粗體只用來加重語氣，例如讀者容易誤會的否定或警告（薪資未知**不會**淘汰職缺）。其他情況不用粗體：條列標籤直接寫「標籤：說明」，識別字、設定值、指令用反引號，介面上的按鈕、選單名稱用「」，段落小標題寫成以冒號結尾的引導句。
- 連結盡量指到章節錨點。
- 流程包含迴圈、判斷、分支時用 mermaid 畫圖，線性流程用編號清單，不用 ASCII 字元畫圖。節點文字含括號、冒號等符號時用雙引號包起來（`A["文字 (說明)"]`），避免解析失敗。目錄結構維持純文字區塊。
- 不用 markdown 表格，理由見[決策紀錄：文件不用 markdown 表格](decisions/no-markdown-tables.md)。依內容改用下列寫法：
  - 屬性清單：一個屬性一項，例如 `- 狀態：✅ 已完成`。
  - 欄位、參數字典：一個欄位一項，寫成「`` `名稱` ``（型態）：說明」。說明有多條規則時用子項條列。
  - 列舉等級：一個等級一項，例如 `- 5：主要工作內容就是目標方向之一`。
  - 索引與對照：一個條目一項，例如 `- [章節](#錨點)：說明`。
  - 有多個屬性的項目：項目本身一項，屬性寫成子項。
  - 真值表、判斷矩陣：改寫成規則句，例如「新資料為 `null` 時保留舊值，其餘寫入新值」。
