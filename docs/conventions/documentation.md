# 文件撰寫慣例

只改文件時讀這份就夠了。改程式碼的慣例見 [development.md](development.md)。

## 語言

文件一律使用繁體中文。

## 文件分區

docs/ 依讀者分成三區，理由見[決策紀錄：產品文件與技術文件分目錄](decisions/product-tech-directories.md)：

- `product/`：產品文件，讀者是 PM、設計師、架構師與工程師。
  - `overview.md`：產品總覽
  - `features/`：功能文件
  - `decisions/`：產品取捨的決策紀錄
- `tech/`：技術文件，讀者是工程師。
  - `architecture.md`：跨功能的技術總覽
  - `tech-design/`：技術設計
  - `decisions/`：技術取捨的決策紀錄
  - `ai-coding-setup/`：AI coding 工具的執行環境
- `conventions/`：兩邊共用的慣例，以及文件與開發流程的決策紀錄（`decisions/`）。
- `docs/README.md`：文件索引與撰寫、使用流程。

依賴只有單向：

- `tech/` 可以連到 `product/`，`product/` 不連到 `tech/`，包含 `tech/decisions/`。
- `conventions/` 兩邊都能連，也能連到兩邊。

## 內容

- 用直白、清楚、簡潔的方式寫，不加修飾。
- 一個功能有兩份文件，依讀者分開（理由見 [決策紀錄：功能文件與技術設計分開維護](decisions/separate-tech-design.md)）：
  - 功能文件 `product/features/<功能 ID>.md`：讀者是 PM、設計師、架構師與工程師。
    - 寫為什麼做、做什麼：使用者故事、需求、業務規則、使用者接觸到的介面與資料、驗收標準。
    - 結構見下方「功能文件的結構」。
  - 技術設計 `tech/tech-design/<功能 ID>.md`：讀者是工程師。
    - 寫怎麼做：系統輪廓、元件之間的約定、資料怎麼存、外部系統的技術限制、驗收對應的測試。
    - 結構見下方「技術設計的結構」。
- 內容放哪一份，問「改掉這段，PM 或設計師需要知道嗎？」：
  - 需要：寫在功能文件，例如薪資換算規則、偏好檔欄位、CLI 參數、結果檔欄位。
  - 不需要：寫在技術設計，例如模組分工、資料表 schema、SDK 的限制、結束碼、測試資料。
- 依賴只有單向：技術設計引用功能文件，功能文件不引用技術設計，實作改變時功能文件才不必跟著改。
  - 功能文件不連到技術設計，也不寫實作方式，例如資料存在哪個資料庫、哪張表、由哪個模組寫入。
  - 提到資料庫時只寫「職缺資料庫」與保存了哪些資訊，不寫資料庫種類、表名、查詢方式與檔案路徑。例外是 CLI 參數說明中 `--db` 的預設值，那是使用者介面。
  - 引用別的功能時，連到該功能的功能文件，引用它的業務規則與對外資料格式。
- 文件描述系統的現況，不寫討論過程（例如「已與使用者確認…」）。決策的結果寫進對應的範圍、需求、規則或技術設計；有替代方案、之後容易被重新提出的取捨，另外寫成[決策紀錄](#決策紀錄)。
- 跨功能的模組依賴、資料存放與技術選型寫在 [architecture.md](../tech/architecture.md)：
  - 只列總覽，細節連到技術設計、功能文件與決策紀錄。
  - 功能的進入點、模組依賴、資料表或技術選型改變時，一併更新。
- 只寫程式碼講不出來的事：規則與理由、外部系統的限制、資料契約。不抄寫函式簽名、完整的 API 呼叫，或逐行翻譯程式碼。
- 流程描述動作與資料流：每一步寫系統做什麼、讀進與產出哪些資料，不寫函式名稱、變數名稱或例外類別。程式怎麼拆成函式由程式碼表達，重構時流程文件才不必跟著改。
  - 功能文件的流程不寫模組名稱。
  - 技術設計的流程寫到模組層級，函式名稱只在元件之間的約定需要時才寫。
- 尚未實作的內容要明確標示，不把願景寫成現況：
  - 功能文件用〔規劃中〕，標記層級見下方「功能文件的結構」，流程見 [docs/README.md](../README.md#撰寫與使用流程)。
  - 技術設計只描述已實作的現況，不標〔規劃中〕，見下方「技術設計的結構」。
- 具體優於抽象：寫出真實的欄位名、檔名、數值，不用「智慧」「高效」這類形容詞。
- 程式碼不引用文件的檔名、章節或編號（見 [development.md](development.md#程式碼與文件的關係)），搬移、改名或重新編排文件時不必改程式碼。

## 功能文件的結構

骨架見 [_feature_template.md](../product/features/_feature_template.md)，為什麼以使用者故事分章見 [決策紀錄：功能文件以使用者故事分章](decisions/feature-docs-by-user-story.md)。以下是骨架背後的規則：

- 「範圍」章直接列出範圍內的內容，不用連結代替：使用者故事縮排成子清單列在這裡，非功能需求與共用規則各一項，冒號後寫章節裡有哪幾件事。範圍內與範圍外用同一種形狀——一項一件事，冒號後寫它的下落，範圍內的下落在本文件，範圍外的下落在別的功能或 TODO.md（都連過去）。讀者在同一個畫面就能對照做什麼與不做什麼，不必跳到別章才知道範圍內有什麼。故事清單只有這一份，不在別章重複。
- 使用者故事是第二層：一個使用者故事一章，是一個可以單獨交付的價值切片。章名寫使用者能做到的事，第一行是「身為…，我想要…，以便…」，章內固定是需求／規則／驗收三小節。同一個故事的需求、規則與驗收要放在一起，不要按「需求」「規則」「驗收」各切一章再用連結互指。功能只有一個故事時也保持同樣的結構，所有功能文件形狀一致。
- 小故事併入所屬故事：只是附帶條件的故事（例如「單筆失敗不中斷整批」）寫成所屬故事的 FR，不單獨成章。
- 角色只寫求職者或開發者：下游功能需要什麼，寫在「輸入與輸出」章，不寫成故事。
- 「規則」小節只放業務規則，以及使用者接觸到的介面與資料（CLI 參數、設定檔欄位、輸出檔欄位），實作方式寫在技術設計。
- 規則放在最先用到它的故事：後面的故事用連結引用，不重複寫。「共用規則」只放跨越各章的業務規則與對外資料格式，例如評分結果的欄位；沒有這類內容時整章省略。
- 非功能需求獨立一章：放在共用規則之前，依範本列出的類別逐一確認。驗收可以直接引用故事章節的 AC。
- 〔規劃中〕標在故事層級：寫在該故事章節的第一行，不寫進標題（標題文字決定錨點，狀態改變時錨點才不會跟著變），該故事內部不再逐條標記。既有故事或共用章節的規則被新故事改到時，在被改到的那一行標〔規劃中〕，因為這些章節的其餘部分已經完成。需求不這樣改，見下一條。
- 驗收預設驗同一章的需求：新故事對既有需求的改動，寫成新故事自己的 FR，既有故事的需求不動，改動的需求和驗收才會在同一章。驗收順帶驗到別章的需求時不另外標註，因為那些需求在自己的章節已經有驗收。每條需求都要有驗收，逐章核對。
- 驗收用業務語言寫 Given／When／Then 與通過條件：
  - 寫「一筆會被淘汰的職缺」「不實際呼叫 AI」，不寫 fixture、假物件、`tmp_path` 或函式名稱。
  - 驗證指令寫在技術設計的[驗收對照](#技術設計的結構)。

功能 ID 同樣用英文簡短描述（kebab-case，例如 `job-scoring`），也是功能文件與技術設計的檔名 `<功能 ID>.md`，理由見 [決策紀錄：功能不再分組，ID 用英文簡稱](../product/decisions/flat-feature-list.md)。

FR 與 AC 的 ID 用英文簡短描述，不用流水號：`FR-<故事 slug>-<重點>`、`AC-<故事 slug>-<重點>`，非功能需求用 `NFR-<重點>`、`AC-nfr-<重點>`。AC 驗的就是同名 FR 時沿用同一個重點名稱。故事只有一條需求時，可以省略 `-<重點>`。這樣讀到 ID 就知道它屬於哪個故事、在講什麼，插入新條目也不必重編既有編號。

- AC 標題只寫 ID 與描述，不列出涵蓋哪些 FR。標題文字決定錨點，列出涵蓋會讓錨點隨涵蓋清單改變，指過來的連結就會失效。
- 內文引用別章的需求時，寫出需求的內容並連到章節，例如「被淘汰的職缺不呼叫 AI（見 [§5](…)）」，不拿 FR ID 當連結文字。

## 技術設計的結構

骨架見 [_tech_design_template.md](../tech/tech-design/_tech_design_template.md)。技術設計有兩個目的：

- 建立整體認知：工程師不讀程式碼，也能在短時間內掌握這個功能的系統輪廓。
  - 元件圖或資料流圖
  - 每個模組一句話的職責與依賴方向
  - 主要流程在元件之間怎麼走
  - 資料存在哪裡、誰寫誰讀
- 記錄程式碼講不出來的事：
  - 設計理由與必須維持的限制，例如某個模組不 import 專案內的其他模組
  - 元件之間的約定，例如爬蟲的 CLI 與互動模式共用哪個進入點
  - 外部系統的技術限制與坑
  - 資料表設計的理由

不寫的內容：

- 函式清單、參數怎麼傳、逐行翻譯程式碼
- 測試 fixture 的內容細節，這些直接看測試程式

判斷一段內容要不要寫：它幫工程師更快看懂全貌，或寫出讀程式碼推不出來的事嗎？兩者都不是就刪。實作方式比需求變動得頻繁，技術設計越精簡越不會過時。

其他規則：

- 依元件分章，不依使用者故事。每章列出它實現的 FR ID，需求才追得到設計。
- 只描述已實作的現況，不標〔規劃中〕：
  - 實作前的技術方案寫在實作計畫或 commit 說明，不進技術設計。
  - 故事完成後，把會長期留下的設計（新的資料表、新的外部限制）更新到對應的元件章節。
- 驗收對照：
  - 依使用者故事分組，順序同功能文件，當作核對故事是否完成的清單。
  - 每條 AC 一項，寫驗證指令，需要網路的標註〔需網路〕。
  - 已實作故事的每條 AC 都要有一項，反之亦然。〔規劃中〕的故事完成時再補上。
  - 型別檢查這類不屬於任何 AC 的檢查，也寫在這裡。
- 跨功能的全貌寫在 [architecture.md](../tech/architecture.md)，技術設計是單一功能內的全貌。

## 決策紀錄

有替代方案、之後容易被重新提出的取捨，寫成決策紀錄，依性質放在三處：

- `product/decisions/`：產品取捨，例如業務規則、功能切分。
- `tech/decisions/`：技術選型與實作取捨。
- `conventions/decisions/`：文件與開發流程的取捨。

檔名是 `<描述決策目的的英文 kebab-case>.md`，例如 `database-selection.md`，不用流水號，搬移或分區時不必重新編號。引用時連結文字寫決策標題，例如「[決策紀錄：資料庫選型](…)」。

一份決策一個檔案，固定三節：

1. 決策背景與問題：為什麼需要做這個決定。
2. 考慮過的替代方案：每個方案一項，寫出未採用的原因。
3. 最終決策：採用的做法，以及它影響到哪些文件。

- 決策紀錄同樣描述現況：決策改變時直接更新原檔，把原本的決策移到「考慮過的替代方案」並寫出不再採用的原因。
- 功能文件、技術設計或慣例在做出該決策的地方連到決策紀錄，理由不在兩處重複寫。

## 格式

- 一段話盡量簡短。一句話涉及多個概念、決策或情況時，改成條列，一個概念一項，不用串在同一句。
- 粗體只用來加重語氣，例如讀者容易誤會的否定或警告（薪資未知**不會**淘汰職缺）。粗體一多，真正要強調的地方就不顯眼。其他情況改用一般字元或結構：
  - 條列開頭的標籤：直接寫「標籤：說明」，全形冒號已經把兩者分開。
  - 程式碼識別字、設定值、指令：用反引號。
  - 介面上的按鈕、選單名稱：用「」。
  - 段落小標題：寫成以冒號結尾的引導句，下面接條列或內文。
  - 名詞、工具名稱與一般的規則敘述：不加標記。
- 引用其他文件時用 markdown 超連結，盡量指到章節錨點。
- 流程圖、架構圖、時序圖等一律用 mermaid 繪製，不用 ASCII 字元畫圖。節點文字含括號、冒號等符號時，用雙引號包起來（`A["文字 (說明)"]`），避免解析失敗。目錄結構清單不算圖，維持純文字區塊。
- 線性流程用編號清單，不畫圖。流程包含迴圈、判斷、分支等邏輯時，才用圖來表達。
- 不用 markdown 表格，理由見 [決策紀錄：文件不用 markdown 表格](decisions/no-markdown-tables.md)。依內容改用下列寫法：
  - 屬性清單：一個屬性一項，例如 `- 狀態：✅ 已完成`。
  - 欄位、參數字典：一個欄位一項，寫成「`` `名稱` ``（型態）：說明」。說明有多條規則時用子項條列。
  - 列舉等級：一個等級一項，例如 `- 5：主要工作內容就是目標方向之一`。
  - 索引與對照：一個條目一項，例如 `- [章節](#錨點)：說明`。
  - 有多個屬性的項目：項目本身一項，屬性寫成子項。
  - 真值表、判斷矩陣：改寫成規則句，例如「新資料為 `null` 時保留舊值，其餘寫入新值」。
