# 專案總覽 — 求職雷達

本文件記錄專案要達成的目標，以及各功能目前做到哪裡。所有文件都描述系統的現況，需求或實作改變時就直接更新：

| 文件 | 內容 |
| :--- | :--- |
| 本文件 | 產品目標、用例、核心技術、功能清單與現況 |
| [features/](features/) | 單一功能的需求、設計與驗收標準，一個功能一份 |
| [conventions.md](conventions.md) | 開發慣例 |

實作某功能時，只需讀本文件加上該功能的文件。

## 產品目標

- 過濾出符合自我發展方向的職缺，避免花大量精力在海量求職平台中人工篩選。
- 了解不同產業、公司現在的發展方向。

## 目標使用者

- 求職者本人（專案擁有者）：想快速掌握符合自己方向的職缺，並得到可信的評分與評語。

## 用例

採用 JTBD 的 job story 格式：「**當**（情境），**我想要**（動機），**以便**（預期成果）。」「我想要」只寫動機，不寫解法。

| ID | 當… | 我想要… | 以便… |
| :-- | :--- | :--- | :--- |
| UC-01 | 我想知道市場上有哪些符合自己方向的職缺 | 不必一頁頁翻求職平台，就能掌握所有相關職缺 | 把時間花在判斷，而不是蒐集 |
| UC-02 | 搜尋結果有上百筆職缺 | 快速知道哪些值得細看、為什麼 | 只把心力放在少數真正符合的職缺上 |
| UC-03 | 我對某個職缺感興趣 | 知道這家公司的狀況與外界評價 | 判斷值不值得投遞 |
| UC-04 | 我在規劃接下來的學習與職涯方向 | 知道各產業、公司正往哪裡發展 | 調整自己的學習重點 |
| UC-05 | 我已經看過一段時間的職缺 | 看清自己實際被哪些職缺或產業吸引 | 確認自己真正想要的方向 |

## 非目標

- 不做多使用者服務、帳號系統或對外公開的網站。
- 不自動投遞履歷。
- 不對求職平台做大量、高頻的抓取（頻率限制見各爬蟲的功能文件）。

## 撰寫與使用流程

1. **新增功能或修改既有功能**：使用者能完成一件原本做不到的事時，才複製 [feature_template.md](feature_template.md) 到 `features/`，依命名規則取檔名，在上表登記，狀態設為 `待規劃`。同一件事換個入口（例如 CLI 改成網頁）或擴大處理量（例如單筆改成批次），或只是規則或結果改變，都屬於修改既有功能，直接修改原本的功能文件：新增或修改的 FR／AC 標上〔規劃中〕，狀態退回 `待規劃`；此時只有〔規劃中〕的條目尚未實作，所屬核心技術的「現況」維持不變。
2. **範圍外的去處**：功能文件「範圍外」的每一項都要有去處。確定要做的新用法，登記到上方功能清單；小改善或技術債，記到 [TODO.md](../TODO.md)；決定不做的，寫進「非目標」。
3. **定稿**：「待決問題」清空後，狀態改為 `待實作`。還有待決問題的功能，不要開始實作。
4. **實作**：狀態改為 `實作中`，依「功能需求」實作，不做「範圍外」列出的事。實作時調整了設計，就同步更新功能文件的「設計」章節。
5. **驗收**：逐條執行「驗收標準」的驗證方式，回報每條結果（✅ / ❌ 與實際輸出）。全部通過後，移除〔規劃中〕標記，狀態改為 `✅ 已完成`，並更新上方所屬核心技術的「現況」。
